# GPG-encrypted pillar — cold-decrypt stress (cherrypy + tornado)

Testing the hypothesis that **cold GPG pillar caches cause flakiness** across
the salt system. Run against the same local salt 3008.1 master+minion, serving
**both** netapi modules (cherrypy :8000, tornado :8001) off one master. Raw
captures in `out/*.json`; scripts in `scripts/`; paths relative to
`research/salt-test-gpg-pillar/`.

**Result: hypothesis confirmed.** Cold GPG-pillar decryption provokes two
distinct failure modes — a tornado **silent incomplete** (200 OK, empty body)
once a single compile is slow enough, and **total unresponsiveness** (all
requests time out) under concurrent compiles — even with a single minion.

## Setup

- Mirrors prod's mechanism: `decrypt_pillar: ['secrets']` + `gpg_keydir:
  /etc/salt/gpgkeys` (prod: `decrypt_pillar: ['secrets:vault']`). A throwaway
  no-passphrase GPG key + N base64-random encrypted secrets are generated by
  `gen-gpg-pillar.sh <N>` (key material and `secrets.sls` are **gitignored**).
- `pillar_cache: False` to force the **cold** decrypt path on every request
  (prod caches with a 1800s TTL, so prod pays this on cache miss / refresh /
  new minion — the cold case we're simulating).
- Triggers: runner `pillar.show_pillar` (master-side render+decrypt) and local
  `saltutil.refresh_pillar`→`pillar.items` (full api→master→minion path).

## Mechanism (why it's heavy)

salt's gpg renderer spawns **one `gpg` subprocess per encrypted value** at
pillar-compile time (`salt/renderers/gpg.py` `_decrypt_ciphertext` → `Popen`),
walking the pillar recursively. So a pillar with N secrets = **N `gpg` spawns
per compile**, synchronously, every time (cache off). Worse, all those
`gpg --decrypt` calls funnel through a **single `gpg-agent`** per keydir, which
serializes private-key operations — so concurrency does **not** parallelize
decryption; it queues behind one agent.

## Finding 1 — single minion, sequential: linear slowness (no hard failure)

`out/stress_results.json`. Decrypt time is ~linear, ~6.5 ms/secret, identical
across modules; nothing errors:

| N | compile time (≈) |
|---|------------------|
| 100 | 0.8s |
| 500 | 3.6s |
| 1000 | 6.5s |
| 2000 | 12s |
| 4000 | 26s |

So one minion just gets **slow**, not broken — confirming the failure needs
either slow-enough compiles to trip timeouts, or concurrency (below).

## Finding 2 — tornado silent incomplete (200 OK, empty body)

`out/silent_incomplete_pillar_items_N2000.json`. Once a compile exceeds
tornado's `local` gather window (~10s, `gather_job_timeout`), tornado returns
**HTTP 200 with an empty body** while the minion is still decrypting — a
**silent false-success**. cherrypy instead waits and returns the full pillar.

| N=2000, `local pillar.items` | result |
|------------------------------|--------|
| cherrypy | 17.0s, **complete** (2000 secrets) |
| tornado  | 10.0s, **`{"return": [{}]}` — empty, HTTP 200** |

A client would see 200 OK and conclude the minion has *no pillar*, with no
error to distinguish "empty" from "timed out mid-decrypt." This kicks in around
N≈1500–2000 (where compile > ~10s); below that both return correctly. It's a
direct consequence of the cherrypy-vs-tornado gather-timeout difference, made
visible by slow GPG decryption.

## Finding 3 — concurrency (the minion herd): total unresponsiveness

`out/concurrent_N1000_K40.json`. Firing **40 concurrent** `pillar.show_pillar`
compiles at N=1000 (each ~6.5s solo) — simulating many minions hitting a cold
cache at once — makes the API completely unresponsive on **both** modules:

| N=1000, K=40 concurrent | result |
|-------------------------|--------|
| cherrypy | **0/40 succeeded**; all 40 read-timed-out at 120s |
| tornado  | **0/40 succeeded**; all 40 read-timed-out at 120s |

The master did **not** 5xx or spew HTML/tracebacks — there was nothing in the
master log. It simply queued everything behind the single gpg-agent (40×1000 =
40k serialized decrypts) so no request finished within 120s. The master
**recovered** once the storm ended (test.ping fine, gpg procs drained). So the
real-world symptom is **hangs / request timeouts / cascading retries**, not a
clean error — which is exactly the kind of "flakiness" that's hard to diagnose.
(K=40 is well past the knee; the tip-over point is lower — not swept here.)

## Implications

**For prod (the hypothesis):** cold GPG pillar is a real, serialized bottleneck.
With many minions checking in after a master restart / cache flush / mass
`refresh_pillar`, their pillar compiles all serialize through one gpg-agent →
fleet-wide slowness and timeouts, manifesting as flakiness in the minions
(pillar fetch timeouts), salt-api (request timeouts / silent-incomplete on
tornado), and anything that reads pillar. Mitigations worth weighing: keep
`pillar_cache` on with a generous TTL (avoid cold storms), reduce secret count
/ split pillar, stagger minion check-ins, or move secrets off per-compile GPG
(e.g. a secrets backend). The single-gpg-agent serialization is the core
scaling limit.

**For the papurika client:**
- **Never treat a 200 as success by shape alone** — tornado returns 200 + empty
  on gather timeout. Cross-check returned minions against the targeted set (the
  non-response detection from the unhappy-path findings) and surface "incomplete
  / timed out," never silently report "no pillar."
- **Expect long / timed-out pillar operations** under cold cache; use generous
  timeouts and prefer async (`local_async` + `/jobs` or `/events`) for anything
  that compiles pillar, so a slow compile doesn't hang a synchronous HTTP call.
- cherrypy waits (slow but correct); tornado bails early (fast but lossy) — the
  client's timeout/retry policy should account for the module in use.

## Reproduce

```bash
bash up.sh                       # master+minion, cherrypy :8000 + tornado :8001
bash apply-salt-patch.sh         # token/cache fix (needs ~/src/saltstack)
./gen-gpg-pillar.sh 5            # baseline; confirms decryption works
uv run scripts/stress.py                       # sequential ratchet (Finding 1)
uv run scripts/capture_silent_incomplete.py    # after gen-gpg-pillar.sh 2000 (Finding 2)
uv run scripts/stress_concurrent.py 1000 40    # concurrency (Finding 3)
docker rm -f papurika-salt-gpg
```
